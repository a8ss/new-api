# 派生模型调用密钥短信通知规格

## Problem Statement

当前 new-api 的密钥派生已经保存外部订单号和联系手机号，并生成模型调用密钥及其分享入口，但派生完成后没有短信通知，也没有按密钥查看发送结果、处理失败或人工补发的能力。归属用户和管理员需要在现有 API 密钥管理流程中完成这些操作，同时不能让短信供应商或日志故障影响已经成功生成的模型调用密钥。

## Solution

以同求宝作为首个短信供应商。密钥派生成功后，根据源密钥对应的短信模板生成正文，异步尝试发送一次；模板中的 `{custom_share_url}` 替换为本次派生密钥的有效分享链接。模板由运维直接维护数据库，供应商连接配置通过环境变量提供。

发送记录必须先创建，才能调用供应商；记录创建失败时不发送短信，派生接口仍返回成功。归属用户可以管理自己的短信，管理员可以跨用户查看和人工发送。系统区分提交和送达，失败或结果未知均不自动重发。回执与上行消息持久化，上行仅管理员可见。数据不自动清理。

## User Stories

1. 作为密钥派生调用方，我希望派生成功后自动向联系手机号发送短信，以便接收人获知密钥已生成。
2. 作为短信接收人，我希望分享链接变量被替换为真实有效的链接，以便直接打开该派生密钥的分享详情。
3. 作为平台运维，我希望按源密钥配置不同短信模板，以便不同来源使用各自的通知文案。
4. 作为平台运维，我希望本期直接维护模板数据，以便无需新增配置页面或模板管理 API。
5. 作为平台运维，我希望只支持明确允许的分享链接变量，以便发现拼写错误而不是把未知占位符原样发给接收人。
6. 作为密钥派生调用方，我希望源密钥没有模板时仍可生成密钥，以便短信配置不阻断主业务。
7. 作为归属用户，我希望没有模板时明确显示未发送原因，以便配置完成后人工处理，且不误用全局默认文案。
8. 作为密钥派生调用方，我希望模板无效或分享入口不可用时仍获得密钥派生成功响应，以便短信失败与密钥生成结果保持独立。
9. 作为密钥派生调用方，我希望短信记录无法创建时系统保留密钥、停止短信发送并保持成功响应，以便避免无法追踪的短信及重复创建密钥。
10. 作为归属用户，我希望在 API 密钥管理处查看每次发送尝试、脱敏号码和错误原因，以便判断下一步操作。
11. 作为管理员，我希望在同一管理入口查看全部用户的短信记录，以便跨用户处理通知问题。
12. 作为普通用户，我希望其他用户不能查询或重发我的短信，以便保护联系信息和分享凭据。
13. 作为平台运维，我希望管理员的短信管理权限不直接披露其他用户的完整模型调用密钥或分享凭据，以便控制授权范围。
14. 作为归属用户，我希望派生密钥没有发送记录时仍可从密钥行菜单人工发送，以便恢复日志创建失败造成的通知缺失。
15. 作为归属用户，我希望人工发送沿用原联系手机号且不重新派生密钥，以便不改变收件对象、外部订单号和已有密钥。
16. 作为归属用户，我希望人工发送使用当前模板和当前有效分享链接，以便不继续发送过时文案或已经撤销的链接。
17. 作为归属用户，我希望分享关闭或不可访问时阻止发送且不自动恢复分享，以便尊重我对凭据披露的控制。
18. 作为归属用户，我希望明确失败的短信允许人工重发，以便修复问题后再次通知接收人。
19. 作为归属用户，我希望结果未知时先确认重复发送风险，再决定重发，以便知道原短信可能已被供应商接受。
20. 作为归属用户，我希望待发送、发送中、待回执和已送达的记录不允许强制重发，以便减少重复短信。
21. 作为归属用户，我希望双击或重复提交人工发送请求不会产生多次发送，以便避免误操作。
22. 作为平台运营者，我希望同一派生密钥的人工发送间隔至少 60 秒、每天最多 5 次，且归属用户与管理员共同计数，以便限制反复发送。
23. 作为归属用户，我希望自动首次发送和幂等重复请求不占用额外人工发送次数，以便限频符合实际操作。
24. 作为平台运维，我希望新派生密钥独立保存源密钥关联，以便即使没有短信日志也能找到正确模板。
25. 作为平台运维，我希望历史密钥不被自动补发或猜测来源，以便避免错误关联模板和收件业务。
26. 作为平台运维，我希望为历史密钥人工补充源密钥关联后再允许发送，以便明确恢复发送的依据。
27. 作为归属用户，我希望删除源密钥不影响既有派生密钥及其短信能力，以便独立管理源密钥和已交付的密钥。
28. 作为平台运维，我希望多个实例不能同时领取同一发送尝试，以便正常运行时每条尝试只提交一次。
29. 作为平台运维，我希望重启后尚未领取的记录能够继续首次发送，以便已持久化的待发送任务不会仅因重启丢失。
30. 作为平台运维，我希望发送失败、超时和发送中断均不自动再次提交，以便优先避免自动重复短信。
31. 作为归属用户，我希望系统区分供应商接受提交与短信实际送达，以便不会把提交成功误认为接收人已收到短信。
32. 作为归属用户，我希望提交满 24 小时仍无最终回执时显示结果未知并允许人工处理，以便记录不会永久停留在待回执。
33. 作为归属用户，我希望迟到回执只更新原发送尝试，以便不会覆盖后来人工发送的结果。
34. 作为平台运维，我希望提前到达、重复或暂时无法匹配的回执被安全保存和去重，以便异步顺序变化不会丢失结果或重复处理。
35. 作为平台运维，我希望回调只有在成功持久化后才确认接收，以便供应商不会因过早确认而丢失事件。
36. 作为管理员，我希望保存并查看手机上行消息，以便了解接收人的回复而不自动改变密钥。
37. 作为管理员，我希望可以手动向同求宝获取上行消息，以便需要时主动获取，而不增加定时轮询。
38. 作为普通用户，我希望系统不凭相同手机号向我展示上行原文，以便不同用户共用号码时不会互相泄露回复。
39. 作为平台运营者，我希望所有用户共用平台配置的供应商账号，由平台承担短信费用，以便本期不引入用户自配账号或余额扣费。
40. 作为平台运维，我希望通过环境变量管理供应商地址、账号、密码和接入码，以便连接配置不通过新增管理页面暴露。
41. 作为平台运营者，我希望发送历史和上行消息不被自动清理，以便保留人工追溯资料。
42. 作为平台运维，我希望新增数据在 SQLite、MySQL 和 PostgreSQL 的新建与升级场景中保持正确，以便现有部署可以升级。
43. 作为控制台用户，我希望短信操作沿用已有组件、语言和可访问性交互，以便在不同语言和设备上理解状态并完成操作。
44. 作为平台运维，我希望日志和审计不包含完整密钥、可用分享链接及供应商密码，以便排障记录不会成为凭据泄露渠道。
45. 作为现有 API 调用方，我希望普通创建密钥和重复外部订单号的既有行为保持一致，以便新增通知不改变原有创建契约，也不因重复派生请求再次发送短信。

## Implementation Decisions

### 业务边界与契约

- 触发点仅为现有密钥派生接口成功创建新的模型调用密钥。普通创建接口不触发短信；派生失败或重复外部订单号冲突不触发发送。
- 模型调用密钥及其源密钥关联先持久化成功，短信记录随后尽力创建。短信记录创建失败时不调用供应商，派生仍返回 HTTP 200 和 `success: true`，保留原有密钥响应字段并附带短信侧状态说明；密钥创建本身失败仍按既有错误契约处理。
- 缺失模板、本地校验失败、供应商明确拒绝、结果未知和最终送达分别展示。未配置或无效模板属于可人工处理的本地提交失败；不能冒充供应商投递失败。
- 平台统一提供同求宝账号并承担短信费用，不扣用户余额，不接入模型额度结算。

### 数据与来源关系

- 派生密钥增加可空的源密钥关联，新派生时持久化；历史数据保持空值。该关联不能只存在于短信日志或操作审计中。
- 新增独立短信模板表，源密钥 ID 唯一对应一份当前模板正文。模板由人工直接改库，不提供模板配置页面或读写 API。
- 每次发送根据模板正文计算版本指纹，保存对应的脱敏文案快照，不依赖运维人工更新版本号或修改时间。
- 新增发送日志表，每次尝试独立留痕，保存派生密钥及归属、源密钥、供应商账号标识、原收件号码、模板版本指纹、脱敏快照、唯一请求标识、供应商消息标识、提交与投递结果、错误码、操作人、时间以及上次尝试关联。
- 新增回执和上行事件表，保存事件类型、供应商账号标识、消息标识、请求标签、号码、状态或上行内容、供应商时间、接收时间、来源、去重标识及可空的发送尝试关联。
- 新表均位于主数据库，不复用计费日志表或独立日志数据库。索引、唯一约束与迁移须支持全部三种主数据库。
- 删除源密钥不级联删除模板、来源关联或短信历史。既有派生密钥继续按保存的源密钥标识查找模板，发送时校验派生密钥本身的状态、归属及分享有效性。
- 不自动补发历史密钥，不按名称、手机号或外部订单号推断来源；运维补充源密钥关联后才允许人工发送。
- 发送日志和上行事件不自动过期或清理。无记录只能显示“无发送记录”，不能推断从未发送。

### 模板与发送内容

- 唯一支持的替换变量为 `{custom_share_url}`，取当前派生密钥的有效分享链接；不支持表达式、脚本、其他变量或任意请求正文。
- 模板直接改库，因此在每次发送前执行正文、未知变量及分享链接校验。没有模板时不发送，不回退到全局默认模板；校验失败不影响派生成功。
- 分享链接须为可发送给手机使用的有效绝对 HTTPS 链接，不接受无法访问的相对地址；分享关闭、密钥状态导致分享不可用或链接无效时拒绝发送，不自动开启或重置分享。
- 自动和人工发送均采用发送时的当前模板及当前有效分享链接。收件号码始终来自派生时保存的联系手机号，不允许人工发送接口更换号码。
- 分享链接能取得完整模型调用密钥，须作为访问凭据处理。短信日志、快照、普通应用日志、审计及调试记录不得保存可用分享凭据、完整密钥或供应商密码，号码默认脱敏展示。

### 调度、状态与人工发送

- 使用发送日志中的待发送记录作为持久化待办，不新增消息队列；后台通过数据库条件更新领取，保证多实例不能重复领取同一尝试。
- 每次领取至多执行一次供应商发送调用；应用、HTTP 客户端和部署代理均不得对短信提交自动重试。不宣称供应商支持幂等提交或端到端恰好一次。
- 未领取记录可在重启后继续首次发送；已经领取但执行中断、提交超时或响应无法确认的记录转为结果未知，不恢复到待发送状态。
- 只有请求整体成功、目标号码提交成功且获得有效消息标识，才显示已提交待回执；不能仅凭 HTTP 成功或响应中的整体状态判定送达。
- 提交与投递结果独立保存。提交成功满 24 小时没有最终回执时转为结果未知，不自动重发；迟到回执仍可更新其原尝试，不覆盖其他尝试的结果。
- 人工发送以该派生密钥当前最新的发送状态判断资格。提交失败、投递失败和结果未知可重发；待发送、发送中、待回执和已送达不提供强制重发。
- 没有发送记录但具有可确认来源的派生密钥允许人工发送；先创建发送记录，失败则不发送，不重新生成密钥或改变外部订单号。
- 人工发送创建新的尝试并关联旧尝试，不覆盖历史。结果未知时前端明确确认重复发送风险，服务端仍执行真实授权、幂等和限频。
- 人工发送请求只提供目标密钥标识和幂等请求标识，不接受任意手机号、文案或分享链接。并发及幂等控制针对同一派生密钥，避免不同浏览器或不同操作人绕过限制。
- 同一派生密钥的人工发送间隔至少 60 秒，每个服务端统一自然日最多 5 次；归属用户与管理员共同计数。自动首次发送不计入人工次数，幂等重复请求不重复计数。

### 同求宝接口

- 仅接点对点发送、被动接收上行和状态报告、主动获取手机上行三个接口。请求使用 UTF-8 JSON 和 POST。
- 点对点发送使用 `action=p2p`，一次请求只发送一条对应一个号码的短信，提供账号、明文协议密码、接入码、号码与内容映射及唯一请求标签；省略号码加密和定时发送参数。
- “非加密”限定为不使用密码摘要或号码 AES 协议变体；供应商地址按用户后续要求支持 HTTP 和 HTTPS，账号与密码放请求体，不放查询字符串。使用 HTTP 时，账号、密码及包含分享凭据的正文会明文传输。
- 发送响应分别检查整体 `status`、目标号码 `result` 及 `mid`。请求标签只用于关联，不能作为供应商幂等保证或回调鉴权凭据。
- 回调接收数组，`flag=1` 处理状态报告，`flag=0` 保存上行；仅在成功持久化后返回供应商要求的 `{"result":0}`。重复事件幂等确认，未能持久化不确认成功。
- 回执按供应商账号、消息标识、请求标签及号码校验关联；提前到达或暂时无法匹配的回执先保存再关联。保留原始状态码，未知状态不能直接当成送达或明确失败。
- 主动获取上行使用 `action=mo`，仅管理员手动触发；默认被动接收推送，不做定时上行轮询。两种入口共用持久化和去重逻辑。
- 手机号不是唯一归属标识，上行不自动绑定某个用户或密钥，不自动回复，也不修改密钥。
- 供应商地址、账号、密码、接入码等通过部署环境变量维护，不增加供应商配置页面或配置 API。配置异常不能变成密钥派生失败。

### 控制台与授权

- 在 API 密钥行菜单提供短信历史和人工发送入口，展示每次尝试的提交、投递状态、脱敏号码和明确失败原因，覆盖加载、空记录、错误与限频状态。
- 管理员增加全部短信记录视图，可定位其他用户的派生密钥并人工处理，包括可定位的无发送记录密钥；上行查询与手动拉取仅管理员可用。
- 普通用户查询和人工发送均限制在自己的派生密钥；服务端校验密钥、发送记录和操作人的归属关系。管理员跨用户操作使用明确的管理员授权。
- 个人访问令牌查询自有记录沿用密钥读取权限。人工发送可能披露完整密钥的分享入口，须同时具备密钥写入和凭据披露权限；模型调用密钥本身不能认证管理接口。
- 复用现有弹窗、确认框、表格、加载和错误组件，接入项目现有国际化、格式化、键盘和响应式规范，不为短信功能另造通用组件。
- 操作审计保留实际操作人、目标密钥、发送尝试和结果，不记录可用凭据。现有认证、会话及请求保护不能仅以界面按钮隐藏或重复发送确认框替代。

## Testing Decisions

- **主要测试边界为管理 HTTP API 与其可观察的发送结果。** 使用真实路由、中间件和业务代码、真实测试数据库及可控 HTTP 短信供应商，验证响应、持久化结果、对外提交和权限；不为每层重复建立测试入口，不 mock 被测业务模块。
- 优先扩展现有密钥派生与分享的 API 数据库矩阵。既有 `TestCustomTokenDatabaseMatrix` 已覆盖真实路由、用户身份、个人访问令牌权限、订单冲突、分享有效性，以及三数据库新建和升级场景，可作为本功能最高层集成测试的基础。
- 后台发送与超时处理只在必要的时钟和调度边界受控，确定性地推进一次处理；外部供应商使用固定请求和响应 fixture，不用真实短信、固定 sleep、随机压测或耗时比较证明行为。

- 并发和限频用例验证：重复幂等标识、不同浏览器并发、用户与管理员并发、60 秒间隔及自然日 5 次共同计数；重复请求不增加提交或计数，自动首次发送不计入人工次数。

### 实现与部署记录（2026-10-16）

- 已实现派生后持久化待办、同求宝单次提交、回执和上行去重、人工发送及后台入口；本节记录实现阶段结果，上文的“未执行测试”描述属于规格发布时状态。
- 部署配置见 `.env.example`：`CUSTOM_SMS_TONGQIUBAO_URL` 为供应商实际 HTTP 或 HTTPS 接口地址，两种协议均用于发送和主动获取上行；另需设置 `CUSTOM_SMS_TONGQIUBAO_ACCOUNT`、`CUSTOM_SMS_TONGQIUBAO_PASSWORD`、`CUSTOM_SMS_TONGQIUBAO_EXTNO`。分享域名沿用 `CUSTOM_TOKEN_SHARE_BASE_URL` 或系统网站地址，必须能生成有效 HTTPS 链接。
- 供应商回调为公开接口 `POST /api/sms/tongqiubao/callback`，按用户后续要求移除 IP 白名单及其配置。仍校验供应商账号、接入码和事件字段，并限制请求大小，仅在持久化成功后确认。供应商未提供签名，本接口不验证发送方身份。
- 运维在主数据库按源密钥 ID 维护 `custom_sms_templates(source_token_id, content)`，例如 `INSERT INTO custom_sms_templates (source_token_id, content) VALUES (123, '【已报备签名】密钥已生成：{custom_share_url}');`。已有模板使用 `UPDATE` 修改正文；版本指纹由发送时计算。历史派生密钥需核实后人工填写 `tokens.custom_source_token_id`，不自动发送。
- 归属用户接口：`GET /api/token/:id/sms-logs`、`POST /api/token/:id/sms-send`。人工发送请求仅包含 UUID 格式的 `idempotency_key`，成功受理返回 HTTP 202。派生成功响应新增 `data.sms`，其中 `not_recorded` 表示记录失败且没有调用供应商。
- 管理员接口：`GET /api/sms/tokens`（可按 `token_id` 定位）、`GET /api/sms/tokens/:id/logs`、`POST /api/sms/tokens/:id/send`、`GET /api/sms/upstream`、`POST /api/sms/upstream/pull`。读取要求 `sms:read`，发送和拉取要求 `sms:operate`；普通用户只能使用自有密钥接口。控制台入口位于 API 密钥行菜单和管理员“短信管理”按钮。
- 回执等待 24 小时后变为未知；领取超过 60 秒仍未完成的尝试标为中断未知，不自动重发。未知状态码（包括文档存在拼写差异的 `REJECTD`）保留原码并提示未知，只有文档明确列举的失败码认定为失败。上行中的 `/ck/` 分享凭据、`sk-` 密钥以及实际生成的 48 位裸密钥在持久化前去敏。
